✓ means checked first-hand on the source, all on 2026-11-02.

## Goal

A workflow can call any public URL, so it can call a published workflow's
`/serve` address, its own included, directly or through an API that calls
back. Each turn of such a loop is a served run holding a run slot while it
waits on the next turn. The server runs at most `CONDUIT_MAX_RUNS` (32) at
once, so a loop fills every slot in moments, and every other workflow is
refused with 503 until it unwinds. That's the server knocking itself over.

Stop that: catch every loop that passes through Conduit, however many
workflows it goes through, and bound the damage of one that passes through
something that drops what Conduit sends. Workflows calling workflows, on
purpose, keep working, a few levels deep.

## What can loop, and what Conduit can see

| Loop | Example | Seen? |
|---|---|---|
| A workflow calls itself | a step in `orders` calls `https://conduit.example.com/serve/orders` | yes: Conduit sends the call and receives it |
| Workflows call each other | `a` calls `/serve/b`, and `b` calls `/serve/a` | yes, the same way |
| Through an API that passes trace headers on | `a` calls an API traced with OpenTelemetry, which calls `/serve/a` while it handles the call | yes, if the hop count rides in a header that API's tracing carries on |
| Through a black box | `a` calls an API that calls `/serve/a` and sends nothing of Conduit's | no: each turn looks like a new caller |

Today a public deployment can be reached by its own workflows, since runs
may call public addresses on 80 and 443. `just dev` and `just up` can't
reach their own server, by the guard's ports and private ranges, so neither
shows it locally.

## What others do

| Who | What it carries | Limit | On a loop |
|---|---|---|---|
| Cloudflare Workers | `CF-EW-Via`: "how many invocations are left", less one per call | 16 | error 1019 ✓ |
| AWS Lambda | a count in its X-Ray trace header | "approximately 16 times in the same chain" | stops the next call, and tells you ✓ |
| Fastly | `Fastly-FF`, whose "primary purpose" is loop detection | 3 visits to one POP, 6 services, 20 hops | 503, "Loop detected" ✓ |
| Dataverse plug-ins and classic workflows | a depth on the execution context | 8 within an hour, configurable | aborts the run ✓ |
| Tyk, between its own routes | a loop count per request | 5, configurable | 500 ✓ |
| Envoy, RFC 8586's `CDN-Loop` | who has seen the request | no earlier visit, by default | 502 ✓ |

Two limits hold for all of them:

- **A header works only where it's carried on.** RFC 8586: "The
  effectiveness of this mechanism relies on all intermediaries preserving
  the header field" ✓. AWS: "Lambda can detect only recursive loops that
  include certain supported AWS services" ✓; for the rest it points to
  alarms on metrics and cost.
- **Anyone can forge it.** "The CDN-Loop header field can be generated by
  any client, and therefore its contents cannot be trusted" ✓. That's fine
  here. A caller who sends a high count is refused sooner. One who drops
  the header could loop without Conduit's header anyway, and the cap in 5
  below is for that.

## Proposal

1. **Every call a run makes carries a trace and a hop count**, in W3C Trace
   Context: `traceparent`, with the run's trace id and a new parent id for
   the call, and `tracestate` with Conduit's own entry first, `conduit=h:3`
   for a call three hops in. Other entries a caller sent go on as they
   came: the spec says a vendor receiving `tracestate` "MUST send it to
   outgoing requests" ✓.
2. **Every request is read for them.** One that comes with a trace
   continues it: the run records the caller's trace id, and its calls go
   out one hop further. One without starts a trace at hop 0, and so does
   one whose `traceparent` doesn't parse, as the spec says: "the vendor
   creates a new traceparent header and deletes tracestate" ✓.
3. **At 8 hops, a run is refused before it starts**: 508, problem details
   with the code `loop`, naming the trace. A loop through Conduit goes
   round 8 times and stops, and its 8 runs share one trace id, so the runs
   list shows the whole loop.
4. **A loop refusal isn't retried.** The upstream client retries 429 and
   every 5xx today; 508 joins what it never retries. The SRE book on why:
   "requests should only be retried at the layer immediately above the
   layer that is rejecting them. … If multiple layers retried, we'd have a
   combinatorial explosion" ✓.
5. **A loop Conduit can't see is held to a quarter of the server.** At most
   a quarter of `CONDUIT_MAX_RUNS` runs of one workflow at once, 8 of 32;
   the next is refused with 503 and `Retry-After`, as the whole server's
   cap is now. A loop through a black box fills its workflow's 8, the
   ninth turn is refused, and the loop unwinds, while the other workflows
   keep their 24. The SRE book's version: "only allowing 25% of your
   threads to be occupied by any one client" ✓.
6. **A step can't set those headers.** A step header named `traceparent` or
   `tracestate` is a problem, `reserved_header`, and the client sets them
   after a step's own headers anyway.

## Decided while drafting, accepted with the plan

1. **The hop count rides in `tracestate`** (your pick), so it survives an API traced
   with OpenTelemetry. W3C Trace Context is a Recommendation, and makes
   passing `tracestate` on a MUST ✓. OpenTelemetry's Java agent, Node SDK
   and Python carry it on by default ✓, as long as the API handles the
   call within the request; Go needs a propagator registered ✓. The cost:
   the spec says "The only purpose of these fields is to enable trace
   correlation" ✓, and a hop count stretches that, as AWS's count in its
   own trace header does. The other places, and why not:
   - W3C Baggage fits the words, "application-defined properties" ✓, but
     it's a Candidate Recommendation, and passing it on is a SHOULD ✓.
   - A header of Conduit's own, as Cloudflare's is, is simplest, and only
     Conduit would carry it on: it catches loops through Conduit alone.
2. **8 hops**, Dataverse's depth and half of Cloudflare's and Lambda's 16.
   Each turn here holds a run open while it waits, and workflows calling
   workflows on purpose go a few levels deep. A constant, until someone
   needs more.
3. **508 for a loop.** It's the registered code named for one, "Loop
   Detected" ✓, though RFC 5842 defines it for WebDAV's "Depth: infinity"
   ✓. None of the gateways above uses it: Fastly answers 503, Envoy 502,
   Tyk 500. A 503 tells a caller to try again later, which never helps a
   loop, and a 502 says an upstream failed, which hides that the request
   itself is the problem.
4. **The response still answers a run whose step got 508.** It goes down
   that step's Unhandled like any failure, so your Fixes check answers
   500. Each level up the loop can then retry the 500 if its step retries.
   Retries are off unless a step turns them on, and every retry meets the
   same 8-hop wall, so this costs runs, not an outage.
5. **A quarter of the server per workflow**, by the SRE book's 25%. It caps
   a busy workflow's legitimate traffic at 8 runs at once too; a setting
   can lift it when one needs more.
6. **Trace ids are recorded and shown, not searched yet.** The run view
   shows a run's trace id. Listing every run of a trace is a filter on the
   runs list, later.

## Someone who drops the headers on purpose

Asked on 2026-11-02: what stops a client or an API that drops the headers
on purpose? Nothing makes a party Conduit doesn't run keep a header.
RFC 8586 says as much of its own: it "can be generated by any client, and
therefore its contents cannot be trusted" ✓. The hop count stops honest
loops: a workflow calling itself, workflows calling each other, an API
whose tracing passes trace context on. Against someone who means harm,
what holds is what Conduit counts itself, on its own side:

| They | What bounds it |
|---|---|
| call `/serve` back without the headers | `/serve` takes a credential: today the one API token, whose holder can do anything anyway; with 07's caller keys, a key per caller, limited and revoked on its own |
| loop a workflow through their API | that workflow's quarter of the run slots: it holds 8, and the rest of the server keeps working |
| fan out: a workflow calls them many times a run, and each call comes back | the same cap: a call past it is refused before a run starts, which costs a request, not a run |
| flood `/serve` with a key they hold | quotas per caller key, the SRE book's "per-customer quotas" ✓: later in 06, as they need 07's keys |

**Workflows within workflows can be checked before they run.** Once a
workflow can be a step of another (07), who uses whom is in the
definitions, and Publish can refuse a cycle in it, as Go's spec makes it
"illegal for a package to import itself, directly or indirectly" ✓: certain,
with no header. A step calling a `/serve` URL as an HTTP step stays the hop
count's to catch, and an API that calls back stays the cap's.

## Left out, and why

- **A check at Publish** for a step calling its own workflow's `/serve`.
  Power Automate warns when saving a flow that "might result in an
  infinite loop" ✓. Conduit doesn't know the address it's served at (the
  editor shows it from the page's own), a templated path can hide the
  slug, and the hop count stops the same loop after 8 turns.
- **Counting the runs of each trace id** rather than hops. More APIs carry
  a trace id than a `tracestate` entry, but a client that sends one fixed
  `traceparent` on every request would look like a loop.
- **A server-wide retry budget**, the SRE book's "only allow 60 retries per
  minute in a process" ✓, **per-caller quotas**, which need 07's caller
  keys, and **deadline propagation**, so every call in a tree shares "the
  same absolute deadline" ✓. Each is later in 06.

## As built

**`internal/trace`** is a package of its own: `httpapi` reads trace
context, `runner` refuses and records, `upstream` sends, and imports point
inward. `Read` takes a request's headers. A `traceparent` that doesn't
parse (uppercase hex, an id of all zeros, version `ff`, a version 00 with
more after it) starts a trace and drops `tracestate` with it; a
`tracestate` member that doesn't parse is dropped alone. `Pass` sets both
on a call: the trace id, a new parent id for each attempt, the sampled flag
only, and Conduit's member first, `conduit=h:N`, then the others, 32 at
most. A count of more than three digits isn't one Conduit sent, so it
counts as none.

**Every request is read for it**, in the router, before anything else. A
run continues the trace its request carries, or starts one, and records
its id (`runs.trace_id`, migration `20261102200000`). The upstream client
sets the headers after a step's own, so a step can't lower the count, and
Publish refuses a step header named `traceparent` or `tracestate`
(`reserved_header`). That's at Publish rather than in Validate, so a
revision published with one still runs, its header overwritten.

**The runner** refuses a run 8 hops in, `ErrLoop`, before it takes a slot,
and the API answers 508, `loop`, naming the trace. A workflow may have a
quarter of the slots, `max(1, CONDUIT_MAX_RUNS / 4)`; past that,
`ErrWorkflowBusy`, a kind of `ErrBusy`, answered 503, `busy`, with
`Retry-After: 5`. The upstream client never retries 508.

**The runs list** shows each run's trace id in full, so a loop's runs show
one id.

**Tests**: the trace package against the spec's own example and each
invalid form it names; the client passing the trace on over a step's own
headers, and starting one without; 508 not retried; the runner refusing at
8 hops, recording and passing the trace on, and holding a workflow to its
share while another runs. Over HTTP, on real servers:
- a workflow calling its own `/serve`: 8 runs in one trace, the eighth's
  call answered 508;
- a call 8 hops in, refused with problem details naming its trace;
- a loop through a stand-in API that drops the trace: held at its share,
  2 runs of 8, while another workflow answers 200. Before the router read
  the trace, the self-call above was stopped the same way, at 8 runs of
  32, the share doing the hop count's job.

**Mutation checks**: 33 on the server, 31 caught at first. A run refused at
the server's cap kept its count against its workflow's share, and a test
now catches that; clearing a count of zero from the map changed nothing, so
it went. On the web, 2, both caught.
